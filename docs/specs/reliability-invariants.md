# 跨阶段可靠性不变量

> 这些问题不属于某一个功能点，而是“功能完成后仍然会坏”的边界。每个 Phase 的验收必须逐条对照，不能只看 happy path 的最终 DB 状态。

## I1 已交付的产物优先于内部依赖

图片/视频/文字已经推给用户后，checkpoint、trace、日志、分析等内部依赖失败，不得把整轮改判为失败。
内部依赖只能是“降级”，不能是“回滚已交付结果”。

## I2 产品数据以 DB 为准，内存只能是缓存

消息、画布、资产一旦落库，任何进程都不能假设自己内存里的版本是最新的。
读画布（API GET、Agent 上下文、inspect_canvas）前必须能从 DB 刷新；跨进程 worker 写入后也必须让读路径看见。

## I3 画布是单权威版本

前端自动保存、服务端作业插画布、Agent 画布命令都是写者，必须带 revision（或等价版本号）。
旧 revision 写入必须失败并触发刷新，不能静默覆盖新元素。

## I4 等待必须有可见状态

请求发出后 300ms 内必须有可见反馈；超过 3s 的操作必须有持续状态（流光/秒数/阶段）。
每个工具调用都要能出现在过程里，并能展开输入/输出/错误；默认折叠，不打断阅读。

## I5 验收必须覆盖四类边界

每个涉及 I/O 或并发的改动，至少验证：

1. happy path
2. 依赖故障/超时（注入或模拟）
3. 两个进程/两个客户端同时读写
4. 旧客户端或旧内存状态（stale write）

只测“本进程、顺序、成功”不算完成。

## I6 错误分层

用户可见失败 / 可降级的内部失败 / 可重试失败要分开。
不要把内部错误直接翻译成红色 `agent_error`；也不要吞掉真正影响交付的错误。

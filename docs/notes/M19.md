# M19 · 生成成功后的假失败、画布落图与动态过程行

## 1. 图片已出却报 `agent_error`

### 根因

trace 显示 `PostgresSaver.putWrites` 在图片 artifact 已经推送后抛：

```
timeout exceeded when trying to connect
  at pg-pool/index.js
  at langgraph-checkpoint-postgres putWrites
```

checkpoint 是执行记忆的加速层，不是产品数据来源；但 runtime 把流末尾的 checkpoint 写入失败当成整轮失败，于是前端在成功图片下面显示红色错误卡片。

### 修改

- `checkpoint-errors.ts`：识别 pg / checkpoint 连接类错误（不把 provider 的 “generation timed out” 误判）。
- `checkpointer.ts`：
  - `put / putWrites / getTuple / list` 失败自动重试两次（400ms、1200ms）。
  - pool max 3 → 5。
- `runtime.ts`：checkpoint 错误且已经产出文字或 artifact → 不发 `run.failed`，发 `run.completed`；trace 记 `checkpoint.write_failed`。
- `onCheckpointUnavailable` → workspace service `rotateThread`：换新 `sessions.thread_id`，旧 thread 的 checkpoint 异步清理。下一轮没有 checkpoint 时用已落库消息历史重建，不会把上下文丢掉。
- 只有 checkpoint 错误、且没有任何输出时才判失败，code 为 `checkpoint_error`。

## 2. 图片没出现在画布

### 根因（两个叠加）

1. **进程内画布缓存陈旧**：worker（或另一个 dev server 进程）直接写 DB 画布，但当前 API 进程的 `workspace.elements` 还是生成前的空画布。`GET /workspace/:id` 只返回内存，下一轮 Agent 的 `<canvas_state>` / `inspect_canvas` 也看到空画布。
2. **旧场景覆盖新画布**：前端自动保存没有版本号，生成作业插入图片后，一个在途的旧空场景保存会把 DB 新元素覆盖掉。

### 修改

- migration `0007_canvas_revision.sql`：`canvases.revision bigint default 0`（已执行）。
- repository `saveCanvas` 必须带 `expectedRevision`，用 `where revision = expected` 条件更新；对不上抛 `CanvasConflictError`，HTTP 返回 409 `canvas_conflict`。
- 服务端插画布后 `replaceCanvas()` 同步内存缓存，并返回新 revision。
- workspace service：
  - `GET` 和每轮 `run` 开始前都从 DB 刷新画布；不再只信进程缓存，多进程也不会看到空画布。
  - 画布保存成功返回 `{ revision }`，前端保存时带回；冲突时提示并在前端刷新。
- 前端：
  - `refreshCanvasFromServer()` 拉最新 workspace，同时更新 `data.elements/files/canvasRevision` 和 Excalidraw 场景。
  - artifact 带 `elementId` 时按新元素 id `scrollToContent(..., fitToContent)`，生成图一定进入视野。
  - 同步失败有 toast，不再静默 `void`。
  - `ApiError` 保留 status/code，409 走专门分支。

## 3. 发送后没有动态过程

- `RunProcess` 之前只在已有工具/思考时渲染；`run.started` 后、第一个 token 前是空白。
- 现在 streaming 状态即使 0 条记录也渲染一行：图标 + 当前动作（思考中 / 正在生成图像 / 正在回答）+ 秒数，默认折叠。
- 新增 `.thinking-shimmer`：一道光反复扫过文字；`prefers-reduced-motion` 时退化为静态灰字。
- 所有已注册工具都会产生一行（之前只记录 generate_image/video/manipulate_canvas）：
  - `offer_choices` 整理问题、`list_assets` 查找项目资产、`get_asset` 读取资产、`inspect_canvas` 查看画布
  - 行内保留输入摘要，展开显示「输入 / 输出 / 错误」，每行可独立展开。
- 工具完成不再覆盖输入摘要，`outputSummary` / `error` 分开存；历史消息兼容旧的 `detail`。
- 请求被服务端受理前（`run.accepted` 还没到）聊天底部也会显示一行 `思考中…` shimmer，不再空等。

## 验证

- 真实生图（另一进程 worker 抢到作业，正好复现多进程场景）：
  - DB `canvases.revision=1`，元素数 1，`customData.assetId` 与 artifact 一致。
  - 修复前 `GET /workspace` 返回 revision 0 / 0 元素；修复后返回 revision 1 / 1 元素。
  - 同一项目追问“现在画布上有几张图？”→ 模型答「1 张：暖秋咖啡海报，375×500」，不再说空画布。
- revision 接口：
  - 初始 0 → 保存 0 得 1；再用 0 保存得 409；服务端插图后 revision=2；旧 revision 保存 409，当前 revision 保存成功。
- 工具行：真实 `offer_choices` 轮 SSE 出现 `tool.started(整理问题)` + `tool.completed(3 个问题)`，`messages.blocks` 同时保留输入/输出摘要。
- server/web typecheck 均 0；测试项目与 Storage 已清理。
